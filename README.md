# MikroTik + GitHub Actions: черновик правила firewall

Первый прототип для **RouterOS 7**. Windows-приложение отправляет запрос в GitHub Actions. Отдельный self-hosted runner с Linux запускает Python-скрипт и подключается к MikroTik по SSH. Winbox используется для просмотра и ручного управления, а не как интерфейс автоматизации. Приложение не устанавливает и не регистрирует runner автоматически.

**Что уже поддерживается:** создание одного *отключённого* IPv4-правила фильтра в цепочке `input`: `accept` или `drop`, TCP или UDP, порт назначения и адрес/подсеть источника. Правило добавляется в конец цепочки и помечается `github-actions-<номер запуска>`. Повторный запуск может создать дубликат. Правило не включается автоматически: порядок правил и наличие более ранних совпадений нужно проверить вручную. NAT, IPv6, другие цепочки, изменение и удаление правил пока не реализованы.

**Статус:** это прототип, не проверенный на реальном MikroTik или в Windows. Не используйте на рабочем роутере без отдельного тестирования. `setup.exe` — автономное приложение, **не установщик**: оно не устанавливает Winbox, runner или системные службы. GitHub-токен хранится только в памяти приложения на время работы; пароль или ключ роутера оно не запрашивает.

## 1. Подготовка GitHub и runner

1. Разместите файлы этого проекта в **закрытом** репозитории и включите Actions. Чтобы запустить workflow вручную, GitHub требует, чтобы файл workflow существовал в ветке по умолчанию. Можно указать другую доверенную ветку в приложении после её публикации.
2. Зарегистрируйте отдельный Linux self-hosted runner в этом репозитории по инструкции GitHub: **Settings → Actions → Runners → New self-hosted runner**. Добавьте ему метку `routeros-firewall` (также нужны стандартные метки `self-hosted` и `linux`). Он должен иметь сетевой доступ к SSH MikroTik на порту 22. На runner необходимы `python3`, OpenSSH client и доступ к GitHub. Runner запускается и обслуживается отдельно от Windows-приложения.
3. В RouterOS включите SSH только для нужной сети, создайте отдельного пользователя с минимально необходимыми правами на чтение и изменение firewall и настройте вход по SSH-ключу. Сначала проверьте ручной вход с runner. Не используйте пароль администратора. Следуйте документации MikroTik для своей конфигурации.
4. На runner получите запись host key: `ssh-keyscan -H -p 22 ROUTER_ADDRESS`. **Не доверяйте выводу автоматически:** независимо сравните отпечаток с SSH host key роутера через доверенный канал/консоль. Запишите проверенную строку (или несколько строк) `known_hosts` для того же адреса, который будет указан в `ROUTER_HOST`. Ключи бывают разных типов. Если адрес или ключ роутера изменится, необходимо заново проверить их и обновить secret.
5. В **Settings → Secrets and variables → Actions** создайте repository secrets:
   - `ROUTER_HOST` — IPv4 или DNS-имя, доступное с runner (без порта; сейчас поддерживается только порт 22);
   - `ROUTER_USER` — SSH-пользователь RouterOS;
   - `ROUTER_SSH_KEY` — полный приватный SSH-ключ без passphrase, разрешённый для этого пользователя;
   - `ROUTER_KNOWN_HOSTS` — проверенные записи `known_hosts` из предыдущего шага.

Ключ и другие секреты доступны выполняемому workflow. Ограничьте права записи в репозиторий, используйте только доверенные защищённые ветки и выделенный runner; не разрешайте недоверенному коду или pull request работать на нём. Пользователь, способный изменить workflow или код в выбранной ветке и запустить его с этими secrets, может получить доступ к роутеру. Не используйте общий runner, по возможности изолируйте его сеть и файловую систему. Скрипт временно записывает ключ и known_hosts в приватный каталог с правами 0600 и удаляет их при штатном завершении; после аварийного прерывания проверьте временные файлы runner. Передавайте секреты только через GitHub Secrets, **не в чат и не в репозиторий**.

## 2. Сборка и запуск Windows-приложения

1. В GitHub откройте **Actions → Build Windows setup.exe → Run workflow**, выберите доверенную ветку с файлами проекта и дождитесь завершения. Workflow также запускается при каждом push в текущую ветку. Скачайте artifact `mikrotik-setup-windows` и извлеките `setup.exe`. Это неподписанный исполняемый файл; Windows может показать предупреждение SmartScreen.
2. Создайте fine-grained GitHub personal access token, ограниченный этим репозиторием, с разрешением **Actions: Read and write**. Для private repository также требуется доступ к репозиторию. Храните токен безопасно и отзывайте при компрометации. Не вставляйте его в чат.
3. Запустите `setup.exe`, укажите `owner/repository`, ветку, токен и параметры правила. Подтвердите отправку. Успешный ответ означает только приём запроса GitHub, а не создание правила.
4. Откройте Actions и найдите запуск **RouterOS - draft firewall rule**. Проверьте его журнал, затем найдите отключённое правило в Winbox: **IP → Firewall → Filter Rules**. Сверьте все поля, порядок и воздействие с остальными правилами. При наличии ошибок удалите черновик в Winbox. Включайте правило только после независимой проверки, имея альтернативный доступ/консоль и проверенную резервную копию. Любое правило firewall может прервать управление устройством.

Для локального запуска без сборки: Windows с Python 3.12 и Tkinter: `python app/gui.py`. Сборка возможна и локально: `python -m pip install pyinstaller==6.11.1`, затем `python -m PyInstaller --onefile --windowed --name setup app/gui.py`.

## 3. Проверка и ограничения

Локальные unit-тесты: `python -m unittest discover -s tests -v`. Они проверяют формирование команды, отклонение некорректных данных и запрос в GitHub, но не заменяют испытания SSH, RouterOS, Windows и реального workflow.

Для испытания на тестовом устройстве сначала сохраните и проверьте резервную копию, убедитесь в наличии физического или иного независимого доступа, проверьте SSH host key и подключение с runner. Отправьте правило с безопасными параметрами, убедитесь в успешном завершении задания и наличии **именно отключённого** правила с нужным комментарием и полями; затем удалите его вручную. Не включайте его во время первоначальной проверки. При ошибке или тайм-ауте сначала проверьте роутер: команда могла примениться до потери ответа. Только после этих проверок можно планировать отдельные сценарии активации и отката.
